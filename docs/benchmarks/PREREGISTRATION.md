## 0. Terms and references

- **Document**: what one Shimmer run reviews (a contract, a filing, a table with its caption, a ContraDoc text).
- **Item**: one scored decision, carrying one benchmark label.
- **Item rule**: the convention the adapter writes for an item, by one item-independent template (section 5.5). Each item has exactly one rule id.
- **Item table**: a file `items.json` written by the adapter beside the bundle, never inside it, with the fields `item_id`, `document_id`, `rule_id`, `benchmark`, and the source ids `source_item_id` and `source_document_id`. It holds no gold label. The B1 tool reads it to know which items to ask; no arm's model sees it, and no arm reads gold.
- **Parts record**: a file `parts.json` written by the adapter beside the bundles: per document the unit id of each part with its source span or index, the split key, side and cluster, the word count and length band, the cut record (budget, prompt overhead, words removed, parts kept whole), and the ids of the items whose marked evidence lies beyond the cut (section 5.3); the build's declared side, the SHA-256 of any split, testmini or exclusion file it read, the frozen-file check of its input where the benchmark has one (section 1), and the documents skipped or excluded. It holds source ids and no gold label (the evidence-beyond-cut list is read from the evidence marks, not from the labels). The adapters, B, C and the scorer read it; no arm's model sees it.
- **Gold**: the benchmark label of an item. It lives in the bundle's `answer_key.json` (which `docs/INPUT_FORMAT.md` section 9 requires to exist and which only the scorer reads) and in role B's folder. Neither Shimmer nor the B1 tool reads it.
- **Opaque ids**: every arm sees only opaque ids. Item id = the first 12 hexadecimal characters of SHA-256 of the UTF-8 string `item:<benchmark>:<source item id>`; document id likewise from `document:<benchmark>:<source document id>`. Benchmark names in these strings are `contradoc`, `cuad`, `scitab`, `findver`, `contractnli`. Source ids appear only in `items.json`, `parts.json` and B's folder, never inside a bundle. Bundle and file names use the opaque document id.
- **Key order**: wherever ids or keys are sorted, they are sorted as key strings (section 1) in code-point order.
- **FLAG, CLEAR, UNDECIDED**: per benchmark, the label an irregular finding maps to, the label for a settled answer or no finding, and what a refusal maps to (section 5.2).
- **ABSTAIN**: no label. Never correct; its role in every metric is fixed in section 4. Coverage is answered items over all items.
- **Silent**: a completed B3 or B2 run with no record of any kind for the item's rule id.
- **Refusal**: a record for the item's rule that carries the UNCERTAIN marker (the UNCERTAIN channel, genesis Part XXV), whatever its `record_verdict`, or a refusal entry naming that rule in the run's `audit/pairing_map.json`. Nothing else is a refusal. The marker is tested as the verifiability gate tests it (`scripts/verifiability_gate.py`): a truthy `uncertain` field, or a `confidence` field equal to `UNCERTAIN` once uppercased. Exact field names: settled from `docs/OUTPUT_FORMAT.md` (section 12 item 1).
- **Figure-audit record**: a record whose `relation` is `missing_field`, `below_band`, `above_band`, `sum_mismatch` or `product_mismatch` AND whose `written_by` field is exactly the string `python` (section 3.6). One definition for every benchmark, with no exception. Python computes these on any figure, label or table in a part, whatever the rules say (`docs/INPUT_FORMAT.md` section 7), and attributes each to a paired rule (section 5.1 says when it decides an item). A record of the same relation that a model wrote (for example a judged absence, `missing_field` with `absence_path` judged) is not a figure-audit record.
- **Run failure**: for a document and an arm, `review_data.json` is missing or unreadable, or the run's completion record is absent, invalid or not `completed`, except for a semantically incomplete run (next term, D-066). The completion record is `<run>/audit/run_completion.json`, written by the pipeline (`scripts/run_completion.py`); B2 writes the same record. It is valid only as `run_completion.read()` accepts it: `schema_version` 1, a known `state`, and for `completed` also `reached_end` true, an integer `exit_code` of 0 and a `finished_at` timestamp. A refusal at start leaves no `completed` record. Exact names: settled, as above. A setup failure (section 5.1, D-084) is not a run failure. For B3 and B4 the record source is the run's bus: a missing or unreadable `logs/agent_bus.jsonl` replaces `review_data.json` in this definition (section 5.1).
- **Semantically incomplete run** (D-066; attacked by the final checker and kept, D-084): a run whose completion record is valid and has `state` `stopped`, `reached_end` true, an integer `exit_code` of 0, a non-empty `finished_at` and `semantic_complete` false. It reached its end, but a model answer it needed failed or came back incomplete (for example a refused producer partition, PAIRING-A). It is not a run failure: its items are labelled from the records it posted (section 5.1, "Incomplete documents"), and sensitivity S-6 shows the reading in which it is one. A run that stopped without reaching its end, or with any other exit code, is still a run failure.
- **Reference material**: none, for all five benchmarks. The B1 prompt shows the single line `None.` B's synthetic tests may carry reference material (grounding files); B1 then shows it (sections 5.4 and 13).
- **Setup failure** (D-084, DEV-014): a B1 or B3 model call that fails out of memory or on a refused attention kernel, or a B1 prompt over the model's context; one rule for both arms (section 5.1). B3's call over its model's context is its own exclusion with the same treatment (section 5.3).
- **Role B**: the test preparer, a session separate from the builder, that draws and holds the holdout sample. **B-dev**: B's session that downloaded each benchmark, applied the split and passed only development items to the lead (D-032). **C**: the scorer role; **C0** is its end-of-S5 run that implements the scorer and these output-to-label rules from this text alone and compares its labels with the adapters' on development outputs (section 12). **R**: the S8 runner.
- **Loop plan**: `prompts/SHIMMER_AUTONOMOUS_LOOP_2026-10-27.md`. S5 is its development runs, S8 its sealed evaluation (S8b preparation, S8c runs, S8d results); S4d, S4e, S4f are its items on arms, this preregistration and the baseline tools; IV.3 is its budget part (S8 allocation, reserve, the 1.3 forecast margin); H3 is its hard spend stop.
- **S8 allocation** (A): 60 USD (the operator's decision D-S12 of 30 October 2026, amending IV.3 and D-S9, which had set 36 USD); the reserve is excluded. Nothing rolls forward from S5: S5's unused allocation is S6's (IV.3, D-081, D-090), so A is 60 USD, and the S8c recomputation of section 2 works within it and cannot raise it.
- **LAW-III**: the constitution's "No self-audit" law (`config/constitution.json`): no model checks output of its own model family.
- **Decisions** in `docs/loop/DECISIONS.md`: **D-019** rejects SummEdits as exposed; its other parts (B-dev could not run in S4, adapters on synthetic items only) were superseded when B-dev ran. **D-032**: the B-dev session, which ran on 27 October 2026 and passed development items for all five benchmarks with a manifest each. **D-038**: the adapters fixed on those development items. **D-039**: the lead's twenty decisions of S4 checker round 2, made before any B1 or B3 development output existed, carried into this text. **D-S3**: the operator's decision of 27 October 2026 accepting ContractNLI's terms of use; only role B downloads it, under that acceptance. **D-S9**: the operator's decision raising the budget (the S8 allocation above).

## 1. Benchmarks, splits, split rules and holdout sampling

| Benchmark | Development | Holdout pool | Document id | Split key |
|---|---|---|---|---|
| ContraDoc | hash rule | the rest | `unique id` (a string) | the near-duplicate group's key (below) |
| CUAD v1 | hash rule (no official development split) | the rest | the contract, identified by the SHA-256 of its `context` text | the document id |
| SciTab | hash rule (no official split) | the rest, minus the demonstration tables (below) | `table_id` | `paper_id` |
| FinDVer | official split `testmini` | `test`, minus any item whose `report` also appears in `testmini` | `report` (the filing's file name) | (official split) |
| ContractNLI | official split `dev` | official split `test` (`train` is not used) | `id` (an integer) | (official split) |

**Hash rule.** The key is the split key as a string: for an integer id, its decimal form with no sign and no leading zeros; for a string id, the string exactly as stored. Where the id is "identified by the SHA-256 of its text", the key is the lowercase hexadecimal SHA-256 of the UTF-8 bytes of that text exactly as distributed, with no normalisation. Compute SHA-256 of the UTF-8 bytes of the key and read the digest as an unsigned big-endian integer. If it is 0 modulo 5, every item of every document under that key is development; otherwise every item is in the holdout pool. The hash is never taken over the item, so all of one document's decisions, and all documents sharing a split key, fall on the same side. This document-level rule replaces, for B-dev, the item-id rule of the loop plan's S4c item 0 ("SHA-256 of the item id, modulo 5"), which B-dev's role file repeats; where the two differ, this section governs (B-dev followed this section: `external/_bdev/BDEV_REPORT.json`, notes).

**Sides are enforced at build.** Every build declares its side (`--side development|holdout`). A document whose recorded side differs from the declared side makes the whole build refuse, writing nothing. Only a build flagged `--development` (development work) may skip the declaration, and `parts.json` records that it did; such a build refuses a document on the holdout side unless `--side holdout` is also given (D-039 item 14). A document's side is the hash rule's for ContraDoc, CUAD and SciTab; for FinDVer, the official split of its items (`split`); for ContractNLI, the side of the frozen file it is read from:

- ContractNLI: an input is accepted only when its SHA-256 is that of the frozen file of the declared side. The development side is the release's `dev.json`, whose SHA-256 the B-dev manifest records (`external/contractnli/MANIFEST.json`, `files_passed_on_sha256`), held by the adapter; a development build of anything but `dev.json` is refused. The holdout side is `test.json`: the manifest records no SHA-256 for it (only for the release zip and the files passed on), so the adapter holds none, and a holdout input is accepted exactly when its SHA-256 equals the value role B records for `test.json` and passes with `--frozen-sha256`; the adapter refuses that value when it is `dev.json`'s, and otherwise relies on B for it. `train.json` is refused for the development side by the held hash, and for the holdout side as long as B passes `test.json`'s. `split` and `bands` apply the same check.

**Demonstration documents.** A document that a benchmark's own paper prints as an in-context (demonstration) example is excluded from the holdout pool, because it is the most likely to have been seen (D-039 item 15). Role B identifies such documents before sampling and passes their source document ids in a file to every build, `split` and `bands` of that benchmark (`--exclude`); `parts.json` records the file's SHA-256 and every document removed, with its item count, and `split` marks them `excluded_demonstration`.

**Filters and groupings applied before the split.**

- SciTab: the paper says 5 tables (25 claims) were held out as in-context examples, but prints only four of them and names no fifth table and no list of the claims (`external/scitab/MANIFEST.json`, `demonstration_tables`). The tables B identifies by caption are excluded from the holdout pool as above. B-dev matched the four printed tables by caption; all four are on the holdout side, so no development item is affected. A table B cannot identify stays in the pool, and the number excluded is reported.
- ContraDoc: documents that share 80 percent or more of their sentences are grouped. A sentence is a run of text ended by `.`, `!` or `?` followed by whitespace, or by the end of the text, compared after collapsing whitespace. The share is shared distinct sentences over the distinct sentences of the document that has fewer. Groups are the connected components of that relation; the group's key is its smallest `unique id` (numeric order when every id is an integer, else string order; the stored ids are strings, not all integers, so string order applies). B-dev computed the groups once, on the whole input (891 documents: 494 near-duplicate links, 642 groups, the largest of 7 documents), with its own implementation of this rule, because the adapter's `split` command was not available to it; that frozen file (`assignments`: group key and side per `unique id`) is held by B with its SHA-256, and its development entries reached the lead (`external/contradoc/MANIFEST.json`). Every build reads groups and sides from the frozen file (`build --assignment <file>`) and refuses a document the file does not list, so a build from a sample never regroups. On the 184 development documents the adapter's own grouping equals B-dev's (125 groups). Before sampling, B runs the frozen adapter's `split` on the whole input and reports the number of documents whose group key differs from the frozen file (expected 0); any difference is entered in the deviation log and settled before B draws. The number of groups and their sizes are reported.
- CUAD: contracts with identical text are merged before the split; the copy whose `title` sorts first is kept, because the source id, the SHA-256 of the text, is the same for every copy. In the release, 1 of 510 entries is such a copy (509 contracts; `external/cuad/MANIFEST.json`). The count is reported.
- FinDVer: a holdout build is given the `testmini` file and refuses any report that also appears in it, and an item whose own `split` names the other official split is refused. The pinned commit holds gold labels for `test` (`external/findver/MANIFEST.json`, `test_gold_labels_present_at_pinned_commit`). At that commit `testmini` holds 700 items over 255 filings and `test` 1,700 items over 439 filings; 155 filings appear in both, so 470 `test` items are removed, leaving a holdout pool of 1,230 items over 284 filings. No filing is on both sides.
- ContractNLI: the `dev` split (61 agreements, 1,037 items) is development and the `test` split (123 agreements, 2,091 items) the holdout pool; `train` (423 agreements) is not used. No agreement id or identical text is shared between the splits (`external/contractnli/MANIFEST.json`). An agreement is identified by the release's integer `id`, which is also its cluster. Every item is one (agreement, hypothesis) pair; its source item id is `<document id>:<hypothesis key>`.
- Counts are taken from the pinned files and reported; published sizes are not used.

**Holdout sampling** (S8, role B). The unit sampled is the document; every item of a sampled document is scored. Sampling is done per benchmark separately, seeded and stratified by label:

- Length band, by the document's words as section 5.6 (Words) counts them, before bundling and before the cut: A under 1,000; B 1,000 to 4,999; C 5,000 to 19,999; D 20,000 or more. S5 measures cost per document in these same bands. B reads every pool document's words and band with the frozen adapter's `bands` command, which writes them over a whole input with no build, and stratifies by it (D-039 item 7). `bands` records each document's side as a build records it (the hash rule, ContraDoc's frozen `--assignment`, FinDVer's official split, ContractNLI's frozen file checked as above), takes FinDVer's `--testmini` (a `test` filing that `testmini` also holds is marked `removed_overlap`, and a FinDVer holdout input without `--testmini` is refused) and `--exclude`, and totals documents, decisions and median words per band for the holdout pool alone (`holdout_pool_bands`), and for the development side apart (`development_bands`); a document on neither side is in neither total. B writes S8's `_handoff/B_SIZES.json` from the holdout pool totals (`holdout_pool_bands`) of that output.
- Label stratum: the share of the document's items whose gold label is FLAG: none; above none up to one half; above one half. For one-item documents this is the label itself. For CUAD, where nearly every contract lacks some category, the label stratum is the tertile of the share of absent categories: cut points from Python `statistics.quantiles(shares, n=3, method="inclusive")` over the pool, a share at or below the first cut point in the first stratum, at or below the second in the second, the rest in the third.
- Strata are length band crossed with label stratum.
- **Seed and generator.** The seed is chosen by role B at sampling time and recorded in B's folder, not here; B records it before drawing anything. The generator is Python's standard library `random.Random(seed)`. Each stratum's documents are sorted by source document id key (key order, section 0) and shuffled in place by `Random.shuffle`, strata taken in order of band then label stratum, from one generator.
- **Order.** At position i (1-based), the deficit of stratum s is p_s * i - taken_s, where p_s is the stratum's share of the pool's documents and taken_s the number already taken from it. B takes the next document from the non-exhausted stratum with the largest deficit; ties go to the lower band, then the lower label stratum.
- B records this full seeded order, so that any prefix of it is itself a stratified random sample (S8c).

## 2. Sample sizes and the benchmark priority list

**Sample sizes: filled by the rule below from S5's measurements (this section, "Sizing from S5"): ContractNLI a pilot of 25 to 26 documents, SciTab and ContraDoc none (version 2, A = 60 USD; version 1, with A = 36 USD, gave 12 to 13); the final n per length band is computed at S8c from `_handoff/B_SIZES.json`. Priority list: ContractNLI, then SciTab, then ContraDoc.**

The priority list holds three benchmarks: ContractNLI, ContraDoc and SciTab. Fit comes first: ContractNLI is High, so it is first; ContraDoc and SciTab are both Medium, and their order is set by measured cost per scored decision, cheapest first: SciTab (about 2.3 minutes of instance time per scored decision on its two current-code development documents) before ContraDoc (about 9.8 minutes per decision; one decision per document). Two of the five selected benchmarks left the list in S5, before B draws any sample:

- **CUAD** (D-073): it has no B3 or B1 development output and no measured cost, so it could not be sized and C0 would have nothing to check on it.
- **FinDVer** (D-078): B3 runs over its model's context on long filings, so section 5.3 would exclude most of them, and B1 failed the 95 percent parse floor at full length, which a prompt revision chosen after both checkpoints' scores are known could not settle honestly within S5's money.

Neither choice read a score. Three benchmarks stay on the priority list, but by the rule below only the first, ContractNLI, receives a sample, and it is a pilot; SciTab and ContraDoc receive none ("Sizing from S5", D-081). So S8 seals one benchmark, as a pilot, beside B's three synthetic tests (section 13). The text below still names CUAD and FinDVer where it defines rules for all five, and SciTab and ContraDoc where it defines their measures; those rules apply to no S8 run.

Fit grades from `SELECTION.md`, the first key of the priority list: ContractNLI High; FinDVer Medium-high; CUAD, ContraDoc, SciTab Medium. (SummEdits is rejected as exposed, D-019.) The second key, measured cost per scored decision: ContractNLI about 3.7, SciTab about 2.3, ContraDoc about 9.8 minutes per decision (below). Fit is the first key, so ContractNLI is first and cannot move down the list by cost; D-038's remark that its cost "may move ContractNLI down the cost-ordered priority list" is corrected here (D-039 item 2). Its cost is met instead by the fallback below.

The rule, written in S4 and applied at the end of S5 (D-081, below):

> First set aside the forecast cost of B's synthetic tests, every arm. Then, in priority order, give each benchmark the smallest number of documents that yields at least 30 documents and at least 100 scored decisions, with B3 and B1 run on every item, at S5's measured cost per document by benchmark and document-length band, with the 1.3 forecast margin (IV.3). When the next benchmark's minimum would pass the S8 allocation, that benchmark gets what is left and is reported as a pilot, and the benchmarks below it get nothing. If allocation is left after every benchmark has its minimum, raise every benchmark by the same fraction until the allocation is used. A benchmark result is reported as a pilot unless it has at least 30 documents and at least 100 scored decisions. The priority list orders benchmarks by fit and then by measured cost per scored decision, cheapest first. It is fixed before B draws any sample.

The S8 allocation A is 60 USD (D-S12, amending IV.3 and D-S9); the reserve is excluded. Nothing rolls forward from S5 (section 0), so A stays 60 USD at S8c.

**ContractNLI's cost fallback, written in S4** (D-039 item 2). ContractNLI was to keep one part per span (section 5.6), so that location stays as fine as the release marks it, unless the trigger fired. The trigger, one formula: if C_span x 30 x 1.3 > A / 2, where C_span is S5's measured B3 cost per ContractNLI agreement with one part per span and A is the S8 allocation (A / 2 is 18 USD), its parts become merged spans (section 5.6, the fallback rule) for every arm and for the rest of the design. The trigger is decided by cost alone. S5 was to measure the B3 cost per agreement under both part rules, on the same development agreements, so that the cost used for sizing under the applied rule is measured, never estimated.

**Applied (D-083, DEV-013).** The span-part measurement (L6s2) failed out of memory, so no complete span-part cost and no lower bound above the threshold exist: the trigger is recorded as undecided, neither fired nor not fired. By the route the S5 plan declared before the measurement (R17), the fallback applies: every arm uses merged parts for the rest of the design, and the sizing below uses the merged-part cost. Merged parts coarsen location (section 9).

How the rule is applied (clarifications beside the rule, not changes to it):

1. **Costs.** At the end of S5 the lead records cost per document by benchmark, length band and arm: B0 (no cost), B1, B2 (laptop, no rented cost) and B3; B4 separately. "Cost per scored decision" in the priority list is the cost of B1 plus B3 per decision; exact ties are broken alphabetically by benchmark name.
2. **Who and when.** The lead applies the rule at the end of S5, before freeze, from the pool's documents and decisions per band in `_handoff/B_SIZES.json`. B-dev wrote that file with, per benchmark and length band, the pool's documents, its decisions (items) and its median word count, by its own reading: the whitespace-separated tokens of each document's raw source strings, a FinDVer table's pipes and separator tokens included, not the word rule of section 5.6. On the development items the two readings place 11 of the 255 FinDVer filings in different bands (D by B-dev's reading, C by the rule) and every development document of the other four benchmarks in the same band (private run summary `bands_development.json`). The S5 sizing therefore uses `B_SIZES.json` only as counts per band (documents, decisions, and the median words of item 4), never to place a document in a band. Its bias has a known direction: for FinDVer it overweights band D, the most expensive band, so the FinDVer forecast errs high (it overstates the cost, which spends less, never more). Every document that is built, sampled, costed or reported is placed by the section 5.6 rule, as the adapters' `bands` command and `parts.json` record it, and S8's `B_SIZES.json` is written by B from the `bands` command's holdout pool totals (section 1). The number of documents n for a benchmark is the smallest n for which n documents with the pool's band shares and mean decisions per document reach both minimums; its forecast cost is n times the band-weighted cost per document, times 1.3. The n per benchmark is entered in this section before freeze.
3. **Prefix.** B's sample for a benchmark is the first n documents of B's seeded order. If those hold fewer than 100 scored decisions, B takes further documents in order until they do, before any run; the forecast is redone and the S8c cut rule applies to the result.
4. **Empty bands.** A length band with no development document takes the cost of the nearest measured band, scaled by the ratio of the two bands' median word counts in the pool (from `B_SIZES.json`; if absent there, by the ratio of the bands' lower bounds, band A counted as 500 words).
5. **The raise and B4.** The core forecast covers B0 to B3. The raise stops at twice each benchmark's minimum. B4 is forecast separately and runs only if the allocation left after that capped raise covers B4 on at least the minimum of the top-priority benchmark. Otherwise the raise continues past twice the minimum until the allocation is used, and B4 is not run.

Documents for each benchmark are taken as a prefix of B's seeded order (section 1).

**The S8c cut rule** (applied before any holdout run, by rule only, if the forecast of the whole design from S5's measured cost per document, by benchmark and length band, with the 1.3 margin, passes the S8 allocation):

1. drop B4;
2. drop whole benchmarks from the bottom of this priority list (fixed before B draws any sample);
3. if the design still does not fit, shorten every remaining benchmark to the same fraction, by taking the first n documents of B's seeded order (section 1), so that the shortened set is itself a stratified random sample.

The resulting n per benchmark is written down before the runner starts, and every cut is reported. S8 aims to seal at least three benchmarks, in priority order. If these rules leave fewer than three that qualify (at least 30 documents and 100 scored decisions), the number sealed is what they give, the reason is recorded, and the shortfall is met together with B's synthetic tests. Applied (D-081): one benchmark is sealed, ContractNLI, as a pilot, and none qualifies; the reason is the allocation (its minimum costs about 55 USD, about 49.6 USD is left after B's synthetic tests; version 2, D-090); the shortfall is met with B's three synthetic tests (section 13). With no non-pilot benchmark, H1 is not tested in S8 (section 4).

|---|---|---|---|---|

| ContractNLI (merged parts) | B | 2 | 59.0 and 90.6 | 17 |
| SciTab | A | 2 | 7.1 and 13.9 | 1 and 8 |

The forecast factor is 1.3 (IV.3), so one minute costs about 0.0280 USD. ## 3. Primary measures

For every benchmark and every arm:

1. **The official metric**, or the closest honest measure with the reason. Each benchmark has one headline metric, the one H1 tests (section 4); every other measure is reported with its interval and not tested:
   - ContraDoc: judgement accuracy (headline), with precision, recall and F1 for "contradictory". Evidence Hit Rate needs BERTScore; it is replaced by exact containment of the marked evidence sentence (whitespace-normalised) and labelled as not the official measure. It is reported on all documents and on the documents of more than one unit alone, since on a one-unit document any unit a B3 finding cites holds the evidence.
   - CUAD: AUPR and precision at 80 and 90 percent recall need a ranked score, which Shimmer's findings do not carry, and span Jaccard needs extracted spans. They are not reported. Closest honest measure (headline): macro-F1 over the two classes present and absent, computed on all (contract, category) items pooled, with precision and recall for "present" at Shimmer's single operating point. Secondary, not tested: the mean over categories of per-category macro-F1, and per-category F1 in an appendix table.
   - SciTab: macro-F1 over supports, refutes, not enough info (headline); the 3 by 3 confusion matrix per arm is reported.
   - FinDVer: accuracy over all items, ABSTAIN counted wrong (headline); coverage and accuracy on answered items beside it. Also per subset as a prespecified secondary breakdown, without tests: the stored `subset` values `ie`, `numeric` and `knowledge` are the paper's FDV-IE, FDV-MATH and FDV-KNOW (development: 250, 250 and 200 items).
   - ContractNLI: accuracy over all items, ABSTAIN counted wrong (headline; H1 tests it). F1 for Contradiction and F1 for Entailment (the paper's other measures) are reported with their intervals, without a test, and the 3 by 3 confusion matrix beside them. The official evidence measures (mean average precision and precision at 80 percent recall over spans) need ranked spans, which Shimmer's findings do not carry; they are not reported. Location recall (3.2) over Contradiction items with marked evidence spans is the closest honest measure, labelled as not official.
   - Never claim comparability with published numbers that use a different metric or split.
2. **Location recall**: over the FLAG items whose evidence is marked (location measurable), the share for which the arm emits the FLAG label and locates the evidence. Unmeasurable FLAG items are not in the denominator; their count is reported.
   - B3 and B2 locate by citing a unit: an irregular record deciding the FLAG whose `unit_id` is a unit containing the evidence, unit ids compared without regard to case.
   - B1 locates by its `evidence` field, split into sentences by the section 1 sentence rule, each whitespace-normalised. On ContraDoc (evidence marked as sentences) B1 is located if any one quoted sentence is contained in a unit that contains the evidence. On FinDVer and ContractNLI (evidence marked as parts, by index) B1 is located if any one quoted sentence is contained in the text of an evidence unit, or contains the text of an evidence unit of at least 5 words (the one word rule of section 5.6), or is contained in the texts of the evidence units joined in document order by single spaces (D-039 item 10); a ContractNLI span is often shorter than the sentence it ends, so containment one way alone would hold B1 to a stricter test than B3. The 5-word minimum keeps a span such as a list marker from being located by any sentence that happens to contain it: on the ContractNLI development items, with one part per span, 10 of the 95 Contradiction items have an evidence part under 5 words, and none has every evidence part under 5 (private run summary `round3_development_counts.json`). Under merged parts, the rule that applies (DEV-013), no Contradiction development item has an evidence part under 5 words (a merged part holds at least 100 words, except the last of an agreement), so the minimum matters only for a short last part (counted in S5 item 10f on development builds of the 61 agreements under both part rules). A contradiction's two sentences usually sit in different units, so the joined string is never required to fit one unit.
   - **The text of a unit**, for every containment test here and in section 3.1: the lines of the written document after the unit's label line (`Passage: part`) up to the next heading, with the escape backslash before a `#` removed, leading and trailing blank lines dropped, and the cut line (section 5.3) included where the unit is the last kept part of a cut document; then whitespace-normalised (runs of whitespace to one space, trimmed). The adapters read it with `benchmark/adapters/common/bundle.py` `read_units`.
   - Evidence units are read on the text as kept after the cut (section 5.3): a unit cut mid-text holds only the evidence that survived, and evidence marked by index on a part cut mid-text is not evidence at all (the item counts as having its evidence beyond the cut).
   - ContraDoc: a unit counts if it contains the evidence sentence or any marked reference sentence. FinDVer: a unit counts if it holds any of the item's context indices (section 5.6). ContractNLI: a unit counts if it is made from one of the spans the item's evidence names, or, under merged parts (the rule that applies, DEV-013), if it holds one of them (section 5.6).
   - A document of one unit makes every B3 FLAG on it located; the number of measurable items in one-unit documents is reported per benchmark.
   - Where the benchmark marks no evidence, where FLAG is an absence (CUAD), or where the bundle holds one unit only (SciTab), location is not measurable: the value reported is recall on FLAG, labelled so.
3. **Reason-confirmed recall**: location catches whose explanation a reviewer marks correct, for B1 and B3 alike. The reviewer sees each catch with the arm label removed, B1 and B3 catches interleaved in a seeded order, and applies one written criterion: "the explanation identifies the conflicting or deciding content and is consistent with the gold evidence". Every catch is reviewed; above 200 per arm and benchmark, a seeded random sample of 200 per arm, reported as an estimate with a document-cluster bootstrap interval. The reviewer is never the builder.
4. **False positives**:
   - Item level: gold CLEAR and predicted FLAG, per arm.
   - Unattached findings (B3 and B2): irregular records whose `source_rule_id` matches no item, and, in a bundle of more than one rule, the irregular figure-audit records of relation `missing_field`, `sum_mismatch` or `product_mismatch` tied to an item (section 5.1; band records decide their rule's item and are never unattached for this reason), counted once by record id in `review_data.json`; the figure-audit share is reported apart. Per-deliverable counts show how many of those record ids appear in each file (`review_data.json`, `review_findings.md`, `tracked_changes.docx`, `document_summary.md`). They change no label.
5. **Refusals**: items mapped from a refusal, documents with a run failure, semantically incomplete documents and the items in them (section 0), and items labelled ABSTAIN with basis `item_calls_failed` (section 5.1); documents and items with a setup failure (section 5.1) and B3 documents excluded for a call over the model's context (section 5.3), each counted apart.
6. **Which layer produced each catch**: Python (computed) or a model (judged), read from the records that decide the FLAG. A record is Python's exactly when its `written_by` field equals the string `python`, compared exactly; any other value, and a record with no `written_by` field at all, is a model's, whatever else the record carries (D-039 item 16). The stamp is the pipeline's WRITTEN-BY-A stamp, on branch `loop/s02`: the pipeline stamps a record `python` only when the post that carried it has backend `paired` or `computed` and a model id starting `python`, and `model` for everything else, including an item no envelope claims. B2 writes the same stamp on every record.

**Comparisons**, per benchmark, on the headline metric of section 3:

- **Primary hypothesis H1** (per benchmark): B3's headline metric differs from B1's. Two-sided, alpha 0.05. As sized (section 2, D-081), S8 samples one benchmark, ContractNLI, and only as a pilot, so H1 is not tested in S8: no p-value, no Holm adjustment and no "better" or "worse" is reported for any benchmark (pilots below). The rule stands as written for any later sealed run that gives a benchmark at least 30 documents and 100 scored decisions; B's synthetic tests are compared as section 13.6 says, never by H1. B3 is called better on a benchmark only if the 95 percent paired cluster-bootstrap interval of (B3 minus B1) lies wholly above 0, and worse only if it lies wholly below 0. Otherwise the result is "no detectable difference", reported with the observed smallest detectable difference. Every per-benchmark call is reported with its Holm-adjusted p-value beside it (the across-benchmarks family below).
- **Across benchmarks**: any statement about Shimmer across benchmarks uses Holm-adjusted primary p-values across all non-pilot benchmarks (family-wise 0.05). It reports how many benchmarks favour each arm, and no pooled metric.
- **Secondary**, Holm-adjusted within each benchmark at family-wise 0.05: the family is {B3 against B2, B3 against B0}, ordered by p-value.
- **B4**: descriptive only, B4 against B3 intervals, no test.
- **Pilots**: point estimates and intervals only. No p-values, no Holm, no wording of "better" or "worse".

**Statistics.**

- Decisions inside one document are not independent (a CUAD contract carries 41). Confidence intervals come from a paired cluster bootstrap that resamples clusters, not decisions. The cluster is the split key (section 1): the document for ContraDoc without a group, CUAD, FinDVer and ContractNLI; the near-duplicate group for ContraDoc; the paper for SciTab. Draw as many clusters as were scored, with replacement; recompute both arms' metric on all items of the drawn clusters (a cluster drawn twice counts twice); take the difference. 10,000 resamples; the 95 percent percentile interval is the 250th and the 9,751st of the 10,000 differences sorted in ascending order (1-based order statistics).
- **Seeds are derived, not chosen** (except the sampling seed, section 1): seed = int(SHA-256 hex of the UTF-8 string `<frozen preregistration SHA-256 hex>:<purpose>:<benchmark>`, base 16) mod 2^63. Purposes: `bootstrap`, `reason-review`, `text-review`. The generator is Python `random.Random(seed)`. A bootstrap resample is n calls of `randrange(n)` over the clusters sorted by their key string in code-point order; the review samples are `Random.sample` over the texts sorted by record id in code-point order. A result computed with any other seed is a deviation.
- **p-values**: for each of the shares of resampled differences at or below zero and at or above zero, the share is (k + 1) / (10,000 + 1), where k is the count; the p-value is twice the smaller share, capped at 1.
- **ABSTAIN in F1-type metrics**: in every F1, precision or recall, ABSTAIN is a prediction of a class that matches no gold label: a false negative for the item's gold class and a false positive for no class. Any precision, recall or F1 with a zero denominator is set to 0, in point estimates and in every resample alike (as scikit-learn's `zero_division=0`). F1 is computed as 2tp / (2tp + fp + fn), as scikit-learn computes it, so its denominator is zero only when tp, fp and fn are all zero. The number of zero denominators and of resamples with one is reported.
- McNemar's exact test is reported for ContraDoc (one decision per document), on correct versus not correct, ABSTAIN counted not correct, as a check; it treats documents as independent and so ignores ContraDoc's near-duplicate groups, which the bootstrap respects; it decides nothing.
- Every result states the number of documents and clusters beside the number of decisions.
- **Smallest detectable difference** (SDD): 2.80 times the bootstrap standard error of the paired difference (two-sided 5 percent, 80 percent power), reported per benchmark. The planned SDD cannot be computed from development variance (D-078): each benchmark has only two or three development documents with current-code B3 and B1 outputs (ContraDoc 2, SciTab 2, ContractNLI 3), and a bootstrap over so few clusters has almost no distinct resamples. So no planned SDD is given before the run. C computes the SDD from the holdout sample, by the formula above, and reports it per benchmark. No other measure stands in for it (not B1 against B0, nor any other pair of arms). The SDD decides nothing: it is reported beside the result, and it neither sizes the sample (section 2 does) nor changes any call. It describes precision; it is not a power claim.
- **Sensitivity**: S-1, S-2, S-3, S-5 and S-6 (section 5.1), S-4 and S-7 (section 5.3; S-7 also scores the items of a document with a setup failure ABSTAIN, section 5.1), and S-8 (DEV-012, worded as `benchmark/adapters/common/mapping.py` computes it, DEV-015): B3 and B4 are scored as if every record a model wrote were absent. Of the document's records only those stamped `written_by` exactly `python` are kept (an unstamped record is a model's, section 3 item 6), and each item is labelled by the same lines of section 5.1 on what remains, so an item a model-written record decided takes the next line, else silence. The run-failure line, the D-066 rules, the over-context exclusion, the setup-failure rule, the rule-id map and the pairing-map refusal entries (Python's own map, not records) are unchanged; the unattached findings under S-8 are Python's alone. For B0, B1 and B2, S-8 equals the primary analysis, and its output says so. All of these are reported beside the primary result; FinDVer also with a cluster bootstrap by issuer, the issuer being the SEC CIK read from the filing's `url` (the number after `/edgar/data/`), recorded per filing in `parts.json` as `issuer_cik`. The ticker in `report` is not used, because one issuer can file under more than one ticker. Every development filing carries a CIK.

## 5. Mapping text and the B1 prompt

### 5.1 Output to label, all benchmarks

Each record is stamped `written_by` from the line that carried it: `python` exactly when `body.backend` is `paired` or `computed` and `body.model` starts with `python`, `model` otherwise; a `written_by` field the item carries itself is replaced. - **Supersession** (INFRA-037), before any line is applied: of the records with the same `item_id`, within one envelope `agent` and document on the bus and within the file for B2, only one is kept: the highest `revision`, then the later `ts`, then the later line or record. A record with no `item_id` is kept as it is.
- **Run failure** (section 0) for B3 and B4: the completion record is absent, invalid or not `completed`, or the bus is missing or unreadable; a line that does not parse is an adapter fault, not a failure. For B2: as section 0 says.

So the same records give the same labels whichever form holds them (held by `scripts/adapter_checks.py`, group `records`, on every mapping fixture). A record belongs to an item when its `source_rule_id` equals the item's rule id, compared without regard to case.

**Figure-audit records** (section 0; D-039 item 3, as settled by the lead in S4 checker round 3 before any B1 or B3 development output existed). One rule for every benchmark, with no exception:

- A band record (`below_band`, `above_band`) belongs to the rule that produced it and decides that rule's item like any other record, in a bundle of one rule or several.
- Python's `missing_field`, `sum_mismatch` and `product_mismatch` records (figure-audit records, so stamped `written_by: python`) decide an item only in a bundle with exactly one rule, where their attribution is not a choice. In a bundle with more than one rule they decide no item in the primary analysis: before the lines below are applied they are set aside, and an irregular one is counted as an unattached finding (section 3.4). The prespecified sensitivity S-3 attributes them as the record says.
- A record a model wrote decides the item of the rule it was posted for, whatever its relation: a judged absence (`missing_field`, `absence_path` judged) for a rule is that rule's answer, on CUAD as on every benchmark.

The reason (P1): Python computes figure-audit records on any figure, label or table of a part, whatever the rules say, and attributes a blank-cell, sum or product record among the rules paired with the unit by the words those rules' texts share with the record's labels, a tie or no shared word going to the first rule in reading order, which follows the opaque ids' hash order; a band record goes to the rule that produced it (`docs/INPUT_FORMAT.md` section 9). In a bundle of several claims the word-based choice is not a check of the item's claim; the band record's is. On the development items all 3 SciTab blank-cell records and 386 of the 779 FinDVer ones (cut bundles; 197 of 1,200 uncut) went to the bundle's first rule and the rest by shared words, and SciTab's 12 band records went to the rules that produced them (private run summary `attribution_development.json`). No rule here declares a `[requires: ...]` field (section 5.5), so every `missing_field` record Python writes on these bundles is a blank-cell record. No rule declares a `[scope: ...]` either, so no pair is ever a judged absence (section 9): CUAD's absent class is not reachable through judged absences. Every CUAD bundle has 41 rules, so on CUAD Python's blank-cell records are set aside, and in the primary analysis CUAD's absent class is reached only by a model-written record of relation `missing_field`, which, from D-068 on, can only be a model's answer kept on a pair Python could compute nothing for (`judged_path` `uncomputable`, `docs/OUTPUT_FORMAT.md` section 5.5); before D-068 such answers were discarded, so B3 could not reach it at all (corrected by D-067). S-3 shows the other reading, as on every benchmark.

An item is a claim about the whole document, judged unit by unit, so a settled answer on any unit beats a refusal on another (D-039 item 1). For each item apply the first matching line:

1. **Run failure** (section 0): every item of the document is ABSTAIN. A semantically incomplete run is not a run failure (section 0); its items take lines 2 to 5.
2. At least one record with `record_verdict` irregular that is not a refusal, on any unit (any relation: `sum_mismatch`, `product_mismatch`, `above_band`, `below_band`, `missing_field`, `date_window`, or a judged finding): the "violated" label, FLAG, except as stated for CUAD.
3. Otherwise, at least one record with `record_verdict` ok that is not a refusal, on any unit (the rule settled and satisfied there): the "holds" label, CLEAR.
4. Otherwise, at least one refusal: the "not settled" label, UNDECIDED.
5. Otherwise (silent, no record of any kind for the item's rule): the benchmark's silence label, CLEAR in the primary analysis. This is Shimmer's real answer in the sense that the run wrote no record for the rule: nothing found that Shimmer keeps. It does not show that a unit was read and found clear: silence also follows when a model's answer was discarded (every judging call on a pair Python could compute nothing for, before D-068), when a reply failed, refused the task or carried no item with the Finding record's shape, and when every answer was refused by Python's quote check; the counts of each are reported per benchmark and arm (section 9, and the run reports' row "Judging calls Python could compute nothing for"). For B2, a plan a model would have answered is listed as not asked (`ablation_not_asked`); that is silence, never a refusal. **Item-level exception** (D-066, B1's failed-call rule applied per item): an item that would be silent is ABSTAIN, basis `item_calls_failed`, when the run's pairing map records at least one judging call for the item's rule and every one has outcome `reply_failed`. A judging call names the registry id; it is matched to the item's rule id through the run's own map (`audit/convention_assignment.json`, `by_rule`, `source_rule_id`, section 12 item 11). Where that map is missing, unreadable or not one to one, the exception is not applied on that document, the row says why (`not_applied_no_rule_map`, `not_applied_rule_map_unreadable`, `not_applied_rule_map_not_one_to_one`) and the document is counted. A refusal entry in `audit/pairing_map.json` that names a registry id is matched through the same map. An item that a record decides (lines 2 to 4) is decided by it whatever became of the calls.

**Setup failures, one rule for B1 and B3** (D-084, DEV-014). The document is left out of that arm's scoring in every analysis but S-7, which scores its items ABSTAIN, and every comparison of two arms leaves out a document on which either had a setup failure (the adapters' `score --paired-with`), as section 5.3 does for a B3 call over the model's context, which keeps its own basis `over_context_excluded`. The labels list the documents with a setup failure, by arm and kind, and count documents and items. B2 calls no model and B4 is not checked (section 5.3). A failed call of any other kind is not a setup failure: for B1 it is an unparseable reply; for B3 it is read by lines 1 to 5.

- **S-3**: Python's `missing_field`, `sum_mismatch` and `product_mismatch` records in a bundle of more than one rule are attributed to the rule they name, as in a one-rule bundle; every other line is unchanged. B0 and B1 are unchanged by it.
- **S-4**: section 5.3 (items whose marked evidence lies wholly in the kept text).
- **S-6** (D-066): every item of a semantically incomplete document (section 0) is ABSTAIN, for B2, B3 and B4 (B0 and B1 carry no completion record and are unchanged by it); every other item keeps its primary label. Reported beside the primary result, with the primary comparison repeated on the complete documents alone (the documents of every arm on which no pipeline arm's run is semantically incomplete).
- **S-5**: the earlier order of the lines above: line 2 (irregular), then a refusal on any unit (line 4), then an ok record (line 3), then silence; for B2, B3 and B4 on all five benchmarks (B0 and B1 carry no records and are unchanged by it). ### 5.3 Cut rule for long documents (all arms)

Stated once, applied by the adapter before bundling, so B0, B1, B2, B3 and B4 receive the same text. The budget is computed per document: the main reading agent's maximum context length (from its own configuration, as recorded in VERSIONS.md), minus the token count of the B1 prompt below with an empty document (the largest over the document's items, rendered from that bundle's own conventions, each item's system turn included, by `benchmark/adapters/common/prompt.py`, the renderer B1 uses), minus the main reading agent's output allowance from the pipeline configuration, minus 32. Tokens are counted with that model's own tokenizer and chat template, loaded from the pinned local checkpoint and passed to the adapter as a counter. The adapter refuses to build without these inputs unless the build is flagged as development, which `parts.json` records. B1 checks every prompt before generating: if a prompt plus the output allowance exceeds the model's context, B1 stops with a non-zero exit, generates nothing and records a setup failure (section 5.1). If the document under review fits, it is not cut. Otherwise the adapter keeps whole source parts (the parts of section 5.6, before they are written as units, so whole units) from the start, in order, while they fit, and appends to the last kept part the line `[Document cut. The remaining N of M words are not shown.]` (no colon, so the line is never read as a field). N and M are words of the source parts, counted by the one word rule of section 5.6 (Words), so M equals the document's word count, the count its length band is read from. If the first part alone does not fit, it is cut at the last whitespace that fits. Reference material is never cut: no benchmark has any. B3 receives the same cut text; how the pipeline divides it across its own calls is part of B3. B3 checks each of its model calls the same way (D-058 condition v): a call whose prompt plus that call's output allowance exceeds its model's context is refused before generating, never truncated and never dropped silently, and recorded in the call's reply record (`context`), as a `prompt_over_context` telemetry event and in the run report's row "B3 prompts over the model context". A document with such a call for any agent is a declared exclusion of B3 (D-078, section 12 item 14): the call is read from the run's reply records, `audit/model_replies/*.json`, field `context`, key `over_context` true. Its items carry basis `over_context_excluded` and are never scored for B3; the labels list the excluded documents with their calls by agent and count documents and items per benchmark. Every comparison of B3 with another arm uses only the documents excluded for neither arm, and with a setup failure for neither (section 5.1; the adapters' `score --paired-with`); every other arm is still reported on all its documents but those of its own setup failures. Sensitivity **S-7** scores every item of an excluded B3 document, and of a document with a setup failure in B1 or B3, as ABSTAIN, so each arm is also reported on all documents. B4 is not checked for this (it is not run where B3's text does not fit). B4 receives the B3 text; if that does not fit B4's context, B4 is not run on that benchmark.

Items whose evidence falls beyond the cut are kept and scored in the primary analysis, since removing them would use the labels. An item's evidence lies beyond the cut when a unit that holds it in the uncut text no longer holds it in the kept text; evidence marked by index (FinDVer, ContractNLI) on a part that was cut mid-text is not evidence (D-039 item 8). `parts.json` lists those items per document before any run. Every report gives, per benchmark, the number of documents cut and the share of words removed (of all the benchmark's words, and of the words of the cut documents), and, per arm, the number of items whose evidence lies beyond the cut; it repeats the primary comparison on the uncut documents alone, and, as the prespecified sensitivity **S-4**, on the items whose marked evidence lies wholly in the kept text (an item with no marked evidence included), every arm on the same items, read from `parts.json`. The magnitude measured on the development items is in section 9.

### 5.4 The B1 prompt, word for word

Sent through the model's own chat template, decoded under the main reading agent's decoding policy, with that agent's output allowance. Text in braces is filled by `benchmark/adapters/common/prompt.py`, which `benchmark/baselines/bare_model.py` and the adapters' cut rule both use; everything else is fixed.

Revision 2 (S4 checker round 1, before any development item): the system turn's last sentence on UNCERTAIN, the reference-material slot, the conventions slot as written in the bundle, the parser's escape repair and UNCERTAIN reading, and the ContractNLI lines. Revision 3 (S4 checker round 2, D-039 item 5, before any B1 development output): the system turn invites the undecided label only on the benchmarks whose rule template asks for UNCERTAIN (SciTab, ContractNLI), so that B1 is not invited to an answer scored as wrong where B3's silence earns CLEAR; on ContraDoc, CUAD and FinDVer the undecided label stays listed and parsed but is not invited. The system turn also says, in one added sentence, that the headings and label lines of the document are markup, not content.

System turn:

```
You are reviewing a document against written rules. You will receive the document, the rules (conventions) that apply to it, any reference material, one item to decide, and the labels you may use. Use the material given; you may use general knowledge to interpret it. In the document, the heading lines (starting with #) and the lines reading Passage: part are markup that divides it into passages, not content; a backslash before a # only keeps a line from being read as a heading, and the bracketed tags after a rule's id only label the rule.

Work through the item first: quote the passages of the document that bear on it, and do any calculation step by step. Then decide which label applies.

End your reply with one line holding one JSON object, and write nothing after it:
{"item_id": "<the item id>", "evidence": "<the exact sentence or sentences of the document your decision rests on, copied from it>", "reason": "<one or two sentences naming the part of the material your decision rests on>", "label": "<one label name from the list>"}

Copy the label name exactly as it is written before the colon in its line.{undecided invitation} A rule that says to emit UNCERTAIN means: use the undecided label.
```

`{undecided invitation}` is a space followed by the sentence below on a benchmark marked "Invited: yes", and nothing on the others. Undecided invitation: `If the material does not let you decide, use the undecided label named below the list.`

User turn:

```
DOCUMENT
{document, after the cut rule, as it stands in the bundle}

CONVENTIONS
{every convention in the bundle as written in it, one per line: its heading without the leading # characters, a colon, a space, then its text}

REFERENCE MATERIAL
{the bundle's reference material: for each grounding file, the earlier version included, in file-name order, its file name on one line and its text below, the files separated by a blank line; the single line None. when there is none}

ITEM
Item id: {opaque item id}
Rule id: {the item's rule id}
{the item's question line, below}

LABELS
{the benchmark's label lines, below}
The undecided label is: {the benchmark's undecided label name}
```

Question lines and label lines:

- ContraDoc. Question: `Decide whether the document contradicts itself: whether two statements in it cannot both be true.` Labels: `contradictory: two statements in the document cannot both be true.` / `not_contradictory: no two statements in the document conflict.` / `undecided: the material does not let you decide.` Undecided label: `undecided`. Invited: no.
- CUAD. Question: `Decide whether the document contains a clause of the category this rule describes.` Labels: `present: the document contains such a clause.` / `absent: the document contains no such clause.` / `undecided: the material does not let you decide.` Undecided label: `undecided`. Invited: no.
- SciTab. Question: `Decide whether the table and its caption support the claim in this rule.` Labels: `supports: the table and caption show the claim is true.` / `refutes: the table and caption show the claim is false.` / `not enough info: the table and caption do not settle the claim.` Undecided label: `not enough info`. Invited: yes.
- FinDVer. Question: `Decide whether the filing supports the claim in this rule.` Labels: `entailed: the filing shows the claim is true.` / `refuted: the filing shows the claim is false.` / `undecided: the material does not let you decide.` Undecided label: `undecided`. Invited: no.
- ContractNLI. Question: `Decide whether the agreement supports, contradicts or does not settle the hypothesis in this rule.` Labels: `entailment: the agreement shows the hypothesis is true.` / `contradiction: the agreement shows the hypothesis is false.` / `not mentioned: the agreement does not settle the hypothesis.` Undecided label: `not mentioned`. Invited: yes.
- B's synthetic tests (section 13; revision 4, D-084, S5 item 10f: added; the five benchmarks' lines and the system turn are unchanged). Question: `Decide whether any passage of the document breaks this rule.` Labels: `violated: at least one passage of the document breaks the rule.` / `holds: no passage of the document breaks the rule.` / `undecided: the material does not let you decide.` Undecided label: `undecided`. Invited: no.

Each label line is one line of the LABELS block. The bare model gets the same document, conventions and reference material as Shimmer, every label with its meaning, room to work, and, where the rules ask for it, Shimmer's abstention option.

**The parser.** Remove every line that is only a code fence (three backticks, with or without a language name). Take the last balanced `{...}` in the reply and parse it as JSON. If that fails, double every backslash that does not begin a valid JSON escape (a valid pair such as `\\` or `\"` is left as it is) and parse once more; a copied `\|`, `\#` or LaTeX command in `evidence` or `reason` must not cost the label. If that fails too, the reply is unparseable. Read `label`; lowercase it, trim it, remove a trailing `(undecided)` and anything from the first `:` on, trim again, and replace `_` with a space. A label that then reads `uncertain` is the undecided label. Compare it with the label names treated the same way; a match gives that label, no match makes the reply unparseable. Each label file records whether the repair was used, and the count is reported. An `item_id` that differs from the item's id is ignored. `evidence` and `reason` are kept for sections 3.2 and 3.3 and never change the label. The parse rate per benchmark is reported.

**Length.** Each label file records the number of tokens the reply used and whether it reached the output allowance (a reply that reaches it may be cut short); the count of such replies is reported per benchmark (D-039 item 11).

**Development check.** In S5, B1 is run on the development items. The B1 prompt and parser may be revised before freeze under the same rules as B3: development items only, every revision logged with its development numbers. A benchmark's development parse rate is its parsed replies over all its development items, pooled over every document (`bare_model.py pool` writes it, `b1_parse_rates.json`; a document's own `b1_summary.json` rate is information only). A benchmark whose pooled rate is below 95 percent has its prompt or parser revised before the freeze, at most three times in all. After the third revision the last revision is frozen whatever its rate, and every benchmark still below 95 percent is reported with its pooled development rate beside each of its B1 results (S-1 shows the effect of its parse failures). The frozen prompt is the last revision.

### 5.6 Document text and units

Every document file is `context/<opaque document id>.md`, named alone in `targets` of `context/_review_targets.json`, with empty `grounding` and `prior`. Its first line is `# D-<opaque document id>`. Then the document's parts follow in order, each as one unit made by a heading (`docs/INPUT_FORMAT.md` section 2):

```
## P-<k, five digits>

Passage: part

<the part's text>
```

`k` counts the parts from 00001 in order (the heading may carry digits; headings are not values). The label line `Passage: part` holds letters only, because every digit in a value is read as a figure (`docs/INPUT_FORMAT.md` section 2; `P-00001` would be the figure -1, which enters products and ratios). It gives every unit the field the rule templates name, so every unit pairs with every rule and no unit is left with no rule (`docs/INPUT_FORMAT.md` sections 4 and 5). A source line that begins with `#` is written with a backslash before the `#`, so it never starts a unit. The adapter records, per document, the unit id of each part and the source span or index it came from. Offsets (character spans) are code-point indices into the decoded text. The parts:

- **ContraDoc**: the `text` field verbatim, one part per blank-line paragraph. No sentence splitter is used.
- **CUAD**: the contract's `context` string, one part per blank-line paragraph.
- **SciTab**: one part only: the caption line (`table_caption`), a blank line, then the table as a pipe-delimited Markdown table, header row first (`table_column_names`), then the separator row, then body rows (`table_content_values`), each cell's text as given with `|` written as `\|`.
- **FinDVer**: the filing `financial_reports/<report>` is an object whose `context` lists its entries `{id, context, type}` in id order from 0; each entry is one part, in index order, so the part at context index k is part k + 1. An entry of `type` `table` keeps its string as given (pipe rows between lines of text), and in each run of pipe rows a separator row as wide as the first row is written after it, unless one is already there (Shimmer reads a table's header only when a separator row follows it); the release almost never has one (3 of the 10,991 development table entries; private run summary `round3_development_counts.json`, held by `scripts/adapter_checks.py`, development group).
- **ContractNLI**: the agreement's `text`, one part per span of the agreement's own `spans` list (the release's segmentation of every agreement into character ranges), in text order. Text the spans leave out, before, between or after them, is not dropped: each such stretch is a part of its own. A span or stretch of whitespace only makes no part. Spans out of order, overlapping or outside the text, or a missing span list, make the build refuse. An item's evidence (indices into that `spans` list) marks the part made from each span it names; an index naming a whitespace-only span marks none, and an index naming no span makes the build refuse. **Fallback, applied when section 2's cost trigger fires or, as in S5, is recorded as undecided (DEV-013); it applies to every S8 run**: the same pieces (spans and the stretches between them, whitespace-only ones dropped) are joined in order into parts, each closed as soon as the text from its first piece's start to its last piece's end holds at least 100 words; the last part may be shorter. A merged part counts as evidence if it holds any span the item names (an index naming a whitespace-only span still marks none). `parts.json` records which rule built the document (`part_rule`) and the spans each merged part holds. On the 61 development agreements the fallback makes 938 parts, a median of 15 an agreement (4 to 39) and a median of 115 words a part, against 5,039 parts, a median of 72 (20 to 255) and 16 words with one part per span (section 9).

**Words.** One rule counts words everywhere: the length band (section 1), N and M in the cut line (section 5.3) and every count in `parts.json`. A document's words are the sum of the words of its source parts above, each counted on the part's source text as the release stores it, before bundling and before the cut. A text's words are the tokens Python's `str.split()` with no argument gives, line by line, except that inside table text a token made only of the characters `-`, `:` and `|` is not a word. Table text is SciTab's column names and cell values (each cell counted on its own) and every pipe row (a line whose first non-blank character is `|`) of a part's source text; a caption and the lines of text around a FinDVer table are not table text, so every token there is a word. So a table's words are its cell words, and the separator row the adapter writes is never counted. A token that a part boundary splits counts once in each part.

## 7. Reported whatever the result, and the stopping rule

**Stopping and changes.**

- No holdout metric is computed until every arm has finished the sized sample, or the hard stop (H3) has ended the runs. The sample is never extended after any holdout result is seen.

- An item whose pipeline run fails is scored as a failure: never dropped, never re-run. Only an infrastructure failure before the item started (instance lost, attach failed) may be re-run, once, paid from the reserve, and the re-run is reported.

## 8. Contamination note

The models may have seen these public datasets, or their source documents, during training. Every report says so. Specifically: FinDVer's test labels have been public since 2026-07-14, so its contamination guard is gone; ContraDoc is built on public web text (CNN/DailyMail, NarrativeQA, WikiText); CUAD's contracts and annotations are public and widely circulated; SciTab's tables come from public arXiv papers and its claims are public, and the tables its paper prints as in-context examples are excluded from the holdout pool (section 1); ContractNLI's agreements come from EDGAR and public PDFs, and LegalBench's ContractNLI tasks are drawn from ContractNLI's test set, so a model that has seen LegalBench has seen ContractNLI test items, and the two are not independent.

The tuned adapters this repository trains (under `tuning/`) were not trained on any of these five sources: a search of every file under `tuning/` for the five benchmarks' names and file names finds none. The base models can still have seen them. The pinned local models (`config/local_models.json`, `config/final_models.json`) are from the Qwen2.5-7B-Instruct release (September 2024) and the Phi-3.5-mini-instruct release (August 2024). ContractNLI (2021), CUAD v1 (2021), ContraDoc (2023) and SciTab (2023) were public before both, so the base models may have seen them. FinDVer's paper appeared in late 2024, after both model releases, and its test labels in 2026; whether its repository or development split was public before the models' training cut-off is not known here, so no claim is made that FinDVer is unseen. The model ids and their release dates are recorded in VERSIONS.md at the freeze beside these dataset dates.

## 9. Limitations, stated in advance

- B's synthetic tests and the builder come from the same model family, so they may share blind spots.
- B's synthetic tests (section 13): three tests are too few for a test of significance; only the spread across them is reported and quoted. The B1 prompt's fixed system turn says that the bracketed tags after a rule's id only label the rule, while a synthetic rule's `[scope: ...]` or `[requires: ...]` tag declares what the rule governs or requires; the format's own example states the requirement in the rule's text as well (`docs/INPUT_FORMAT.md` section 3), and section 13.1 asks B to write every rule so, so B1 is not denied it, but it reads the tag as a label where Shimmer reads it as a declaration. B1's location on a synthetic test is read from a quoted sentence that only one unit holds, and its reason is a reviewer's, while B3's reason is checked against the key's typed claim; section 13.5 makes the comparison of the two on one footing.
- The order of preregistration, freeze, sampling and run is attested only by local records.
- The adapters were written on synthetic items and then corrected on the development items; a release fact no development item shows (SciTab's `not enough info` spelling: no development claim carries that class) is unconfirmed, and the UNDECIDED path cannot be checked on SciTab development items.
- Location recall is coarse for B3 on one-unit documents (any FLAG there is located): 123 of the 184 ContraDoc development documents are one part (64 of the 103 contradictory ones), and every contradictory development document has its evidence sentence inside a single part (private run summary `round3_development_counts.json`; held by the checks' development group), so ContraDoc's evidence containment is also reported on documents of more than one unit (section 3.1). Section 3.2 reports the one-unit count. B1 is held to quoting a sentence that meets an evidence unit; on FinDVer and ContractNLI containment either way is enough (section 3.2).
- Per-unit judging (D-039 item 1): a document judged unit by unit gives many records per item. A settled answer on any unit decides, so a single wrong ok on one of many units can turn a NotMentioned (or a refusal) into Entailment; ContractNLI agreements have about 83 units each on the development items with one part per span, and under merged parts, the rule that applies (DEV-013), a median of 15 (4 to 39; 938 parts over the 61 agreements). The share of items with both a refusal and an ok record is reported per arm.
- **Merged parts coarsen ContractNLI's location** (DEV-013). A merged part holds a median of 115 words (16 with one part per span). On the 61 development agreements the evidence parts of a Contradiction item hold a median of 10.4 percent of its agreement's words (mean 11.7, at most 44.1) under merged parts, against 4.8 percent (mean 5.5, at most 21.1) with one part per span, and a median of 1 evidence part against 2 (counted in S5 item 10f on development builds under both rules). So a B3 citation, or a B1 quote, that lands anywhere in that larger stretch counts as located: location recall under merged parts is a coarser measure than the span-level one the release supports, and is not comparable with it. Span parts could not be run on the A10 (L6s2 ran out of memory on one development agreement, D-083).
- Figure-audit records (section 5.1): in a bundle of more than one rule Python's `missing_field`, `sum_mismatch` and `product_mismatch` records are set aside in the primary analysis; band records decide their own rule's item. On the development items every B2 FLAG on SciTab and FinDVer came from a figure-audit record (`SELECTION.md`, Dry-run results): under section 5.1 B2 flags 2 SciTab claims, both from band records, and no FinDVer claim, so B2's primary analysis there is close to B0's; S-3 shows the other reading. The same rule holds on CUAD, whose 41-rule bundles leave its absent class to model-written `missing_field` records in the primary analysis; a B2 run on CUAD therefore flags no absence there, and S-3 shows Python's blank-cell records attributed.
- ContractNLI's NotMentioned class is reached only when no unit settles the hypothesis and some unit refuses; silence counts as Entailment, so a run that says little about a hypothesis scores as Entailment.
- CUAD's official ranked metrics cannot be produced; its headline measure is not comparable with published numbers.
- The cut rule removes text equally for every arm, which understates any arm built to read long documents; FinDVer filings are the most affected. Measured on the development items with the real counter (the main reading agent's pinned tokenizer and chat template, a 32,768-token context and a 2,048-token output allowance; private run summary `cut_summary.json`): FinDVer, 209 of the 255 filings cut, 45.2 percent of all their words removed (48.0 percent of the words of the cut filings), and 283 of the 700 items (40 percent) with their evidence beyond the cut; CUAD, 11 of 96 contracts cut (13.0 percent of all words, 33.0 percent of the cut contracts' words; CUAD's answer spans mark where a clause is, but the CUAD adapter records no evidence units, because FLAG is an absence and location is not measurable for it, section 3.2, so no CUAD item has evidence beyond the cut, 0 items). ContraDoc, SciTab and ContractNLI were not recounted with the real counter; with the stand-in counter of S4 (one token per word) nothing was cut on them (private run summaries `contradoc_summary.json`, `scitab_summary.json`, `contractnli_summary.json`). Silence earns B3 CLEAR on such items, so S-4 is reported beside the primary result (section 5.3).
- The producer was trained and evaluated under eager attention with its prompt prefilled in one shot (`tuning/producer_v3/experiment.json`), so its 102-of-102 development figure is an eager, one-shot figure, and the ordinary runs v5 to v12 ran it so. B1 and B3 run it under sdpa attention pinned to the memory-efficient backend, prefilled in one shot (option A, section 4; D-063), because in one shot under eager attention neither a B1 prompt near the full context nor B3's per-document producer prompts on the longer documents fit the instance's memory (INC-015), and the first remedy, chunked prefill under eager (E, D-060, D-061), missed the threshold declared for it. sdpa computes the same attention as eager up to floating-point rounding, so a reply can differ in a token from the eager reply. Measured on development items before the freeze (L3e, D-063; the replay of B3's own 12 producer prompts from L2 entry 02 on the tuned checkpoint, one A10, exposed): sdpa one shot against one-shot eager, 12 of 12 replies byte-identical, 9 of 9 on the prompts of three chunks or more; E against one-shot eager, 8 of 12, 5 of 9 on the long prompts, against D-061's declared threshold of 90 percent; E against its repeat, 12 of 12. Peak GPU memory allocated: one-shot eager 18.97 GB, sdpa 10.97 GB, E 9.47 GB; prefill seconds over the 12 prompts: sdpa 18.8, one-shot eager 30.3, E 41.6. D-061's declared fallback then adopted whichever of E or sdpa was byte-identical to one-shot eager on more items of the same set: sdpa (12 against 8; 9 against 5). Earlier, L2 measured sdpa (not pinned) against eager on 21 short development items: 18 of 21 tuned replies byte-identical (85.7 percent), labels agreeing on 20 of 21 (D-060). The figures of both arms that run the producer are therefore sdpa figures, not the eager figures the producer was trained and evaluated on, and a reply may differ in a token from what the eager producer would write; on the measured set it did not. B1's peak GPU memory at a full-length prompt under sdpa was measured before the freeze (L4b, 30,565 tokens, development): 18.6 GiB allocated with the base checkpoint and 20.9 GiB with the tuned one, so it fits the A10. An out-of-memory error in S8 is a setup failure under section 5.1's one rule for B1 and B3 (DEV-014), counted apart and left out of every comparison.
- "No kernel difference" holds for the producer only: the models `_load_qwen` loads (VERIFIER, PRACTICE_AUDITOR, FACT_CHECKER) run sdpa, pinned to the memory-efficient backend, one shot, in B3 (D-061 item 8); B1 has no such call.
- **Discarded judgments, before D-068** (D-067). In paired mode a model is asked about a unit and a rule only where Python's checks call for it. On the text-only claims of all five benchmarks Python computes no figure, so every such pair is a judging call of plan kind `uncomputable`, and until D-068 the model's answer on such a call was discarded by design (outcome `advisory_not_kept`). Measured on the development runs before D-068 (counts, development, exposed): every phase 5.5 judging call on the benchmark claims was of that kind with that outcome (187 calls on ContractNLI, 174 on FinDVer, every call on ContraDoc and SciTab), Python wrote no record on those claims, and B3 therefore equalled B0 item for item on ContraDoc, SciTab, ContractNLI and FinDVer. Any development figure from those runs is a figure of B0's labels and is labelled with its size (for example one ContractNLI agreement).

Only items with the Finding record's shape are kept: a reply whose items carry no declared `relation` or no `record_verdict`, or an UNCERTAIN marker on an item without them, keeps nothing, and the pair stays silent. D-068 changed no prompt and no rule template, and no benchmark development output was used to shape it. L5v (D-069, D-070), on tests that are not benchmarks: on the clinical sheet 1 judging call on an uncomputable plan, its answer kept; on the device log, flawed, 26 such calls and 3 answers kept; on its clean twin 32 such calls and 8 answers kept as a model's records. - B1 decides one item per call and sees each item alone; B3 reviews the whole document in one run. This difference is part of what the primary comparison measures.

- The rule templates are fixed text; a different wording could change every arm's result.
- B1's checkpoint (section 12 item 12) is chosen on development items by the stronger of two baselines (the higher pooled development headline among the checkpoints that meet the parse floor), never by B3's result.

## 13. B's synthetic tests

Written in S5 item 10f (D-084, DEV-016), before role B prepares any S8 synthetic test, from the input format (`docs/INPUT_FORMAT.md` sections 9 to 11) and the repository scorer's matching (`tools/score_corpus.py`). The adapter is `benchmark/adapters/synthetic/adapter.py` (shared core `benchmark/adapters/common/`); C implements the same from this section.

### 13.1 The tests

Role B prepares three tests, independently, in the input format. Each test is six bundles: the flawed document, its clean twin and four perturbation probes (`docs/INPUT_FORMAT.md` sections 10 and 11), each bundle with its own single-version `answer_key.json` (`planted`, `clean`, and `twin_of` on the flawed document and its twin). A bundle whose key is negotiation-style (`prior_records`) is not scored by this section and is reported as not scored. Every rule B writes states in its text whatever its `[scope: ...]` or `[requires: ...]` tag declares (section 9). The tests are sealed: B prepares them; no arm and no builder sees a key.

### 13.2 Items

One item per (document under review, rule): each document the bundle's targets file names under review (`context/_review_targets.json`, or `_review_targets.json` at the top of a staged workload), and each rule heading of the bundle's conventions that carries an operator id (`docs/INPUT_FORMAT.md` section 3), each id once. The answer key is never read to make items. Item id: the first 12 hexadecimal characters of SHA-256 of the UTF-8 string `item:synthetic:<bundle folder name>/<document file stem>/<rule id>`; document id: the document's file stem, the id the pipeline and B1 use. The item table (`items.json`, written beside the bundles) holds `item_id`, `document_id`, `rule_id`, `benchmark` (`synthetic`), `bundle` and the source ids, and no gold; it is the table `bare_model.py` and `tools/stage_workload.py --items` take.

Gold of an item: FLAG (`violated`) when the key plants at least one flaw under the item's rule in that document, else CLEAR (`holds`). The test has no undecided class.

### 13.3 Arms

B0, B1, B2, B3 and (if run) B4 as section 4 defines them, on every bundle of every test, the twin and the probes included. The cut rule (section 5.3) does not apply: no synthetic bundle is cut. A B1 prompt over the model's context is a setup failure (section 5.1).

### 13.4 The B1 prompt for a synthetic item, word for word

The system turn is section 5.4's, with the undecided invitation empty (Invited: no), word for word:

```
You are reviewing a document against written rules. You will receive the document, the rules (conventions) that apply to it, any reference material, one item to decide, and the labels you may use. Use the material given; you may use general knowledge to interpret it. In the document, the heading lines (starting with #) and the lines reading Passage: part are markup that divides it into passages, not content; a backslash before a # only keeps a line from being read as a heading, and the bracketed tags after a rule's id only label the rule.

Work through the item first: quote the passages of the document that bear on it, and do any calculation step by step. Then decide which label applies.

End your reply with one line holding one JSON object, and write nothing after it:
{"item_id": "<the item id>", "evidence": "<the exact sentence or sentences of the document your decision rests on, copied from it>", "reason": "<one or two sentences naming the part of the material your decision rests on>", "label": "<one label name from the list>"}

Copy the label name exactly as it is written before the colon in its line. A rule that says to emit UNCERTAIN means: use the undecided label.
```

The user turn is section 5.4's template with the synthetic question and labels; text in braces is filled by `benchmark/adapters/common/prompt.py`, everything else is fixed:

```
DOCUMENT
{the document under review, as it stands in the bundle}

CONVENTIONS
{every convention in the bundle as written in it, one per line: its heading without the leading # characters, a colon, a space, then its text}

REFERENCE MATERIAL
{the bundle's reference material: for each grounding file, the earlier version included, in file-name order, its file name on one line and its text below, the files separated by a blank line; the single line None. when there is none}

ITEM
Item id: {opaque item id}
Rule id: {the item's rule id}
Decide whether any passage of the document breaks this rule.

LABELS
violated: at least one passage of the document breaks the rule.
holds: no passage of the document breaks the rule.
undecided: the material does not let you decide.
The undecided label is: undecided
```

The parser is section 5.4's. `violated` is FLAG, `holds` is CLEAR, `undecided` is UNDECIDED, which is ABSTAIN here (no undecided class; counted as coverage). An unparseable reply is ABSTAIN (S-1 maps it to CLEAR).

### 13.5 Labels and measures

**Labels.** B2, B3 and B4 by section 5.1's lines, through the one record reader, with D-066 (semantically incomplete runs and `item_calls_failed`), the rule-id map, the over-context exclusion and the setup-failure rule. One reading differs from the five benchmarks: every record decides the item of the rule it names, Python's `missing_field`, `sum_mismatch` and `product_mismatch` records included, in a bundle of any number of rules. The input format makes the test's author write each rule so that such a record goes to the rule the key names (`docs/INPUT_FORMAT.md` section 9, "Which rule a finding is attributed to"), so the attribution is part of what is tested, not a guess; S-3 therefore equals the primary analysis and is reported as equal. A FLAG of B2, B3 or B4 carries the records that decided it (its unit, relation, field label, figures and `written_by` stamp). A FLAG of B1 carries the units its quoted evidence lies in: each quoted sentence (section 1's sentence rule, whitespace-normalised, a closing `.`, `!` or `?` dropped) locates the one unit whose whitespace-normalised text holds it, and a sentence that two or more units hold locates none and is counted. Units are Shimmer's (`pairing_map.split_units`: a unit per heading below the top level, `u<NN>-<slug>`, and the preamble unit `u00-<slug>`).

**Measures**, per arm and analysis, per bundle, per role (flawed document, twin, probes) and per test:

1. **Location recall** over the planted flaws of every scored bundle. B2, B3, B4: a planted flaw is located when a record that decided a FLAG of the document, under any rule, has a unit id that contains the planted `unit` (case-insensitive) and the planted `relation` (any relation when the key gives none): the matching of `tools/score_corpus.py` and of the input format, on the records that decided a FLAG only (an ok record or a refusal locates nothing). The rule is not used to locate (input format section 9); **attribution**, whether a locating record is under the planted rule, is reported apart. B1: located when its item of the planted rule is FLAG and a quoted sentence lies in the planted unit (B1 states no relation; its rule is the item's).
2. **Reason-confirmed recall.** B2, B3, B4, computed: among the locating records, one whose relation equals `claim.relation`, whose field label equals `claim.field_label` when both state one (lowercased, trimmed), and whose two figures include both claim figures (rounded to 6 decimal places, order ignored); a planted flaw with no `claim` is reported as unverifiable, never confirmed. B1: by the reviewer under section 3.3, with the key's claim as the gold reason. The comparison of B3 with B1 on this measure uses the reviewer's verdict for both arms (section 3.3 applied to every location catch of each), and B3's computed figure is reported beside it.
3. **False positives**: items flagged whose rule the key plants nothing under; unit-rule pairs flagged on units no planted flaw names (B1: the units its quotes locate), with, for B2, B3 and B4, how many of those records each of section 3.4's deliverables shows; and unattached records (section 3.4).
4. **Distractor hits**: unit-rule pairs flagged on a unit the key lists as `clean`.
5. **Clean-twin false alarms**: for each flawed document, its twin's flagged items and flagged unit-rule pairs, from the same arm's labels of the twin.
6. **Refusals and failures** as section 3.5: items from a refusal, ABSTAIN items, B1 parse failures, run failures, semantically incomplete documents, setup failures and over-context exclusions, each counted apart.
7. **The catch layer** (section 3.6): located by Python's records, a model's, or both.

Every analysis of section 4 is computed: S-1, S-2, S-3 (equal to the primary), S-5, S-6, S-7 and S-8. Every B3 value is printed beside its S-6 value, the value on the complete documents alone (with the counts of complete documents and of documents in all) and its S-8 value.

### 13.6 Comparisons and what may be quoted (Annex A 11.11.3)

Each measure is reported per test and arm. Across the three tests the report gives the spread: each test's value, the smallest, the median and the largest. No number is pooled over tests, and no p-value or interval is computed across three tests. A statement that one arm's measure is higher (or lower) than another's **holds across tests** only when it holds, in the same direction, in each of the three tests (a tie in any test breaks it); it is stated with the spread, and otherwise it is stated as not holding across the three tests. In public text only the spread across the three tests may be quoted, never one test's number alone, and only when all three tests were sealed and run on the one frozen commit. The ContractNLI pilot is reported beside the tests with point estimates and intervals only; it is never a number that holds across tests, and H1 is not tested on it (section 4).
