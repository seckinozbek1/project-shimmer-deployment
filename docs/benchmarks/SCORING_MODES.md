# Scoring modes: benchmark and as shipped

Rule text written 30 October 2026, 13:53 (+03:00, system clock), in the advice lane of loop S5, before the rule was run on any output. It implements D-S13 item 9 (Seckin, 30 October 2026): in benchmark and test scoring, every model judgement that the pipeline shows as advice counts as a finding; a user's review does not change. **This rule was chosen after development scores had been seen** (the S5 development scores of B1, B3 and B2 on ContraDoc, SciTab, ContractNLI, FinDVer and CUAD existed when Seckin decided it and when this text was written). Nothing in it depends on which items are right: it reads stamps, fields and the run's own rule-id map, never gold, labels or scores.

It is a scoring mode of the benchmark adapters (`benchmark/adapters/common/`), chosen with `label --scoring benchmark|as_shipped`. It changes no run output: the pipeline still shows advice as advice (HONEST-OUTPUT-A), never promotes it, and writes nothing differently in either mode.

## 1. What the pipeline shows as advice

Advice is a judgement a model wrote that the pipeline shows to its reader marked "Written by a model. Not promoted to an amendment. Not checked by Python." (`docs/OUTPUT_FORMAT.md` sections 5 and 7.4). In a run's machine-readable output it takes these forms:

| Form | Where it is | Carries a verdict field? | Counted today (`as_shipped`) | Counted in `benchmark` |
|---|---|---|---|---|
| A. A model-written typed record that names the operator's rule id (`source_rule_id`): a D-068 answer kept on a pair Python could compute nothing for (Python's stamped copy, `judged_path` `uncomputable`), a judged absence (Python's stamped copy, `absence_path` `judged`), or an auditor's or analyst's own typed record | bus; `review_data.json` `model_findings_not_promoted` | yes (`record_verdict`, or the UNCERTAIN marker) | yes, for that rule | yes, unchanged |
| B. A model-written typed record that names only the registry id (`rule_id`, `procedure_id`, `conv_id` or `convention_ref`, no `source_rule_id`), for example a VERIFIER record | bus (no `source_rule_id`); `review_data.json` `model_findings_not_promoted`, where phase 6 shows it under the operator's id read from the registry | yes | no: it names no item's rule, so it decides nothing (an irregular one is an unattached finding) | **yes**, for the operator's id the run's own map gives its registry id (section 2) |
| C. A model's note on one of Python's findings (`explanation_by` `model`) | the Python record's `explanation`; the amendment comment, quoted and labelled | no: a sentence, never parsed | not separately (the Python record it rides on is counted) | not separately: it is a sentence about Python's record, not a judgement of its own; counted by number |
| D. A judged absence's raw model copy | bus line with the call's `call_id` | yes | no (the stamped copy is counted once) | no, unchanged (counted once, by the stamped copy) |
| E. An answer Python refused (D-068 `uncomputable_refused`, judged absence `absence_refused`) | pairing map entry `{unit_id, rule_id, relation, reason}`; a count in `reviewed_document.md` | no verdict is recorded outside the raw reply text | `absence_refused` entries are refusals (UNDECIDED); `uncomputable_refused` is not read | unchanged: shown as refused, not as advice |
| F. A reply's items withheld from its own post (`items_withheld`; every judging call but a judged absence; before D-068 `advisory_not_kept`) | only the raw reply under `audit/model_replies/` | not shown | no | no: not shown to the reader at all |
| G. Model items that are not typed records (no `record_verdict` and no UNCERTAIN marker): a LEGAL_ANALYST `verdict`, a VERIFIER `finding`, an extraction | the raw reply JSON in `reviewed_document.md` ("a technical record") | no `record_verdict` | no | no: not a finding in the Finding record's vocabulary, and reading a meaning into another verdict word would be a keyword table (WORDS-A) |
| H. Editorial-board observations (phase 6.5) | `reviewed_document.md`, heading "Editorial review board (advisory: written by models, ...)" | a deliverable-quality verdict, not a record verdict | no | no: they name no rule and no unit |

So the one form the pipeline shows as advice for a rule and that today's reading does not count is B. Forms A and D are already counted as today's section 5.1 counts them; C, E, F, G and H carry no verdict in the Finding record's vocabulary, or name no rule, or are not shown as advice, and decide nothing in either mode.

## 2. The rule (benchmark mode)

Benchmark mode labels each item exactly as the primary analysis does (preregistration section 5.1, lines 1 to 5, the run-failure line, D-066, the over-context exclusion, the setup-failure rule, the figure-audit set-aside, the pairing-map refusal entries, supersession), on one changed set of records:

1. **Advice record.** A record (section 5.1's definition: it carries `record_verdict`, or the UNCERTAIN marker and a rule) whose `written_by` stamp is not exactly `python` (an unstamped record is a model's).
2. **Attribution through the run's own map.** An advice record whose `source_rule_id` is absent or empty is given an operator id before any line is applied: its registry id is the first non-empty of `rule_id`, `procedure_id`, `conv_id`, `convention_ref`, in that order; its operator id is the `source_rule_id` that the run's own map (`audit/convention_assignment.json`, `by_rule`, read as section 12 item 11 and D-078 read it: compared without regard to case, used only when the file is readable and one to one) gives that registry id. The record then belongs to the item whose rule id equals that operator id, compared without regard to case, like any record. The record is marked `source_rule_id_from_map: true`.
3. **Left as it is.** An advice record that carries a `source_rule_id` keeps it (never replaced by the map); an advice record with no registry id, a registry id the map does not hold or maps to an empty id, or in a document whose map is missing, unreadable or not one to one, keeps no operator id, decides no item, and is counted (`advice_unmapped`, with the map's status). A record stamped `python` is never changed.
4. **Precedence between advice and Python's records.** None by writer. Every record that belongs to an item, Python's or a model's, takes part in the same lines in the same order: an irregular record that is not a refusal on any unit gives FLAG (on CUAD only when one has relation `missing_field`, else CLEAR); otherwise an ok record that is not a refusal gives CLEAR; otherwise a refusal (an UNCERTAIN record or a pairing-map refusal entry) gives UNDECIDED; otherwise silence. So when advice and a Python record for the same item disagree, the irregular one decides, whichever wrote it; when an ok and a refusal meet, the ok decides. Python's `missing_field`, `sum_mismatch` and `product_mismatch` records in a bundle of more than one rule are set aside before the lines as in the primary analysis; an advice record is never set aside, whatever its relation.
5. **Unchanged.** Everything else of section 5.1, 5.3 and 5.4: the run-failure line; D-066 (semantically incomplete documents, `item_calls_failed`); the over-context exclusion and the setup-failure rule; the judged absence counted once by Python's stamped copy; the prior-relation fault; the unattached findings (now without the advice records that step 2 attributed to an item); B0 and B1 (they have no advice; their labels are the same in both modes).
6. **Sensitivity analyses** are computed on the benchmark-mode primary exactly as on the as-shipped primary. S-8 drops every record not stamped `python`, so S-8 is the same in both modes: it is the score with no advice counted.

**As shipped** is today's reading, unchanged: an advice record belongs to an item only by the `source_rule_id` it carries.

## 3. What the labels and scores carry

- Every analysis in a labels file carries `scoring`: `benchmark` or `as_shipped`; every analysis in a metrics file carries the `scoring` of the labels it was scored from (`as_shipped` for a labels file written before the modes existed, which is today's reading).
- In benchmark mode, each pipeline document row carries `advice`: the advice records read (`records`), those attributed through the map (`mapped_by_rule_map`), those left without an operator id (`unmapped`) and the map's status (`rule_map_status`), the notes on Python's records (`notes_on_python_records`), and the pairing map's refused answers (`refused_uncomputable`, `refused_judged_absence`); the counts add `advice_records`, `advice_mapped_by_rule_map` and `advice_unmapped`. As-shipped labels carry none of these, so they are byte for byte today's labels apart from `scoring`.
- Reports show the two numbers side by side, each labelled: the benchmark-mode score (advice counted; the main figure) and the as-shipped score. Note: today's reading already counts form A, so the score with no advice counted at all is S-8 (section 2, item 6); a report that means "advice not counted" quotes S-8 and says so.

## 4. Where it is built and held

- `benchmark/adapters/common/mapping.py`: `SCORING_MODES`, `advice_view`, `label_pipeline_arm(..., scoring=)`.
- `benchmark/adapters/common/cli.py` and `benchmark/adapters/synthetic/adapter.py`: `label --scoring benchmark|as_shipped` (default `as_shipped`, so no existing caller changes silently; the main figure is labelled with `--scoring benchmark`).
- `scripts/adapter_checks.py`, group `scoring`: executed fixtures for both modes (every advice form of section 1 counted or not as the table says), with a neutralisation that must fail.
