# Loop understanding

My restatement of `prompts/SHIMMER_AUTONOMOUS_LOOP_2026-10-27.md` (the spec, gitignored, never committed), written before S0 as I.3 requires. Plain English, numbered. Where this file and the spec differ, the spec wins.

## A. How the loop runs

1. One lead session (this one) runs I.0, then I.3, then S0 to S14 in order, until `docs/loop/private/LOOP_STATE.md` says DONE or every remaining stage is BLOCKED. It never ends its turn while work remains, never asks a question, and never waits idle. Questions and Class S items go to `docs/loop/private/FOR_SECKIN.md`.
2. Precedence when instructions conflict: Part II hard limits; Annex A as amended by Annex B; Part IV machinery; Part V stages; Part III decision profile; my judgement. I.0 is a checklist inside Part I. Parts VI and VII apply as written unless a higher part conflicts. A conflict not settled by this order is decided by P18 and recorded in `docs/loop/DECISIONS.md`.
3. Nothing said in chat binds unless the spec says it. The start message's extra notes (session started by `.claude/start_loop.ps1` with flags; a refused settings write is recorded and the loop continues) are operator context, consistent with I.0 item 3's own fallback.
4. Reading check (I.3): read every line; write this file; a fresh checker compares it with the spec; fix every item; repeat until a checker returns zero items or three rounds pass; record the rounds here. The spec is silent on items still open after round three; my reading: record each remaining item and why it stays open in the "Checker rounds" section, then proceed (P19).
5. Per-stage mini-check: before building, write `docs/loop/stages/S<NN>_PLAN.md`; a fresh checker compares plan and spec; every plan item maps to a spec line and every spec line to a plan item before building.
6. After any compaction, restart or resume: re-read the spec, `LOOP_STATE.md` and the newest handoff; a fresh checker compares the handoff with the current stage's spec; fix gaps; assume every teammate is gone.
7. Style (I.4): plain English, short sentences; no em dashes in anything I write or change (existing em dashes in untouched text stay; no mass edits); define each new term where it first appears in reader documents; no personal paths in new tracked files (write `<USER_HOME>`); no collaborator name ever; no real party names. Never write `<USER_HOME>` inside a settings file: permission rules need `//c/Users/<name>/...`, commands need `C:/Users/<name>/...`. Commit messages end with the harness attribution lines.
