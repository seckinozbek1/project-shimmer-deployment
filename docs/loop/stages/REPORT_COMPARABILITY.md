# The comparability rule for the technical report (D-S74 item 3, D-327)

Written 8 November 2026 by `demo-console` and committed by the lead (the harness refuses report files written by a subagent), before any figure is drafted into `docs/TECHNICAL_REPORT.md` and before the confirmatory read. Revised 9 November 2026 for the fifteen gaps `report-check` found (D-329): the revision changes the rule where a gap asked, applies it again to every row, and replaces the open points with their outcomes. Revised again on 9 November for the lead's rulings of D-362: condition 3 applied as written, T's half B demoted to its verdict, a factor coordinate and the same hardware type (D-S82), and G1's models named from the run records. A fresh checker reads each revision before the report uses it. Every printed figure comes from a named run file or decision.

## 1. What is compared

A result is one figure with seven coordinates: run, arm, benchmark, item set, metric, scorer and factor record. The arm is B3 (the shipped system), B1 (the bare model) or a named judging form. The factor record (D-S82 item 1, D-362) lists every factor that differs between the result and its comparison: machine type, model or checkpoint, training recipe, calibration, prompt or context, code commit, decoding setting, item set, scorer, and the random seed where one exists. D-S82 requires it to be written by Python from the run's own records, not by hand. That tool is `judge-product`'s, on `lane/factors`, not yet merged (D-341, D-362). Until it is, every factor note in this file is marked "written by hand, to be regenerated by the D-S82 tool" (read by hand from the runs' records). The report prints no factor column until the tool writes it, and no figure is printed in the report before the tool has written its factor record. A difference is attributed to a factor only when that factor alone differs, or when an isolating run exists; otherwise it is called joint and the factors are named together. Two results are comparable when all five conditions of section 2 hold for both. A result enters the results section in one of two ways:

- beside a comparable result: its B1, its untrained form, or its published counterpart under section 5;
- as the one figure of its kind, with the report saying so.

## 2. The five conditions (D-S74 item 3's four, and a fifth under D-S82)

1. **Same metric.** The same quantity under the same named definition, checked for each arm on its own:
   - the scoring mode (`detection_dev`, `v2_primary`, `benchmark`, or a bar's rows) and the averaging;
   - the function that reads each arm's answers into labels, named per arm;
   - the treatment of silence, refusals and unreadable answers, which follows from that function.

   Two arms read by different functions (a quote-screened reader against a bare-reply parser, an agent-reply reader against a B1 reader) do not share a metric, whatever it is called, unless a decision written before the read says how the two readings are made equal. A metric renamed or redefined between runs is a different metric.
2. **Same item set, or a declared subset,** identified by a digest or a named file, checked for each arm on its own.
   - A subset counts only if it was declared before any of its figures were read, by a commit older than the output it is read from: a half fixed by `split-report`, or a sample fixed by a decision written with no output on it. Its digest is named beside every figure.
   - The basis of selection is printed beside the subset. A subset chosen on an outcome (for example, the partitions that had failed) measures the repair of that outcome, never a rate on the benchmark.
   - After failures, the item ids each arm counts must still be the same, and the number of failed entries and the items they held are printed beside the figure. A set that lost items after the read (a failed entry, a void row, a dropped unreadable reply) is not the same set, unless the bar written before the read said how such items count.
3. **Same scorer.** The same scoring code by content, and the same keys.
   - The code is identified by the tree of the commit the scoring ran at (its git tree id), or by a digest of every module the scorer imports. One file's blob is not the scoring code.
   - The read's working directory is named: a committed tree, or a working tree whose difference from that commit is recorded.
   - The keys are identified by a recorded key digest, where the scorer writes one.
   - A decision that names no commit or digest leaves this unverified, and unverified counts as failed until a named file settles it.
   - **Applied as written (D-362):** a row whose read's working directory is not recorded is demoted. It is printed as a measured method finding, not a result, unless a record of the working tree at read time exists. A read made on the instance by the sealed code has such a record: the bundle's project tree was verified against its sealed commit before the launch (`AUTHORIZED_LOCAL_REVERIFICATION.json`, `project_tree_verified`), and the read's output was written by that code into the run's evidence. A read made afterwards on this machine has one only if its output or a decision names the commit and a clean working tree.
4. **A completed run with integrity passed,** on every entry the result counts.
   - Stopped, refused, out of memory or `semantic_incomplete` fails it for that entry.
   - A pass that rested on a repair later removed (the K8 stamp, ENVELOPE-B) is not a pass.
5. **The same hardware type** within a comparison (added under D-S82, D-362), named from the run records (`launch.json`, `instance_type`). Every run in this inventory ran on `gpu_1x_a10` (all 230 `launch.json` files under `external/s05`, compare-check round 2). A figure from another type is set beside an A10 figure only as a hardware factor, never as a like-for-like result. Whenever a new machine type is used, the same configuration also runs a fixed small reference set on it and on the A10 (D-S82 item 3). That pair gives the type's time factor and shows whether any score moved; under deterministic decoding none should, and if one does, it is reported as a hardware effect, not a system gain. A result from a new type with no such reference pair is not compared with any A10 result. D-S79 makes faster types the default for coming runs, so this binds the fresh-set read.

## 3. Three readings beyond D-S74's words

- **(a) Exposure (accepted, D-329; widened for gap 3).** A figure is in-sample when its material was chosen, tuned or thresholded on, or when the same items were read earlier and the method was shaped by what that reading showed. Examples: a half A that chose a threshold; a combination chosen in sample; items whose B1 replies were read in an earlier run before the form under test was designed. It may be printed, labelled in-sample with the earlier reads named, but never set beside an out-of-sample figure as the same thing (LESSONS L-4).
- **(b) Within one run (accepted, D-329; narrowed for gap 1).** Two arms scored in one run share the run and its integrity record, and nothing more. Conditions 1 and 2 are still checked per arm (the same read function and refusal treatment; the same item ids after failures, with the failed-entry count printed), and condition 3 for the scorer. Sharing a run is never by itself a reason to compare.
- **(c) One read over several completed runs (new, gap 5).** A read that scores the outputs of several runs together (for example, C base and T against J1's B1 replies) is admissible only when:
  - each source run is named with its integrity and its evidence archive's digest;
  - the read names every source's item ids;
  - conditions 1 to 3 hold across the sources as they would within one run.

  Reading (b) never applies across runs.

## 4. Scope (gaps 4 and 10)

- **In scope:** results on the report's public benchmarks (ContraDoc and SciTab; ContractNLI, CUAD and FinDVer only where a row says so), from the loop's cloud runs and replays, and ablations within those runs.
- **Out of scope as results, kept as method findings or context:**
  - the synthetic development suite and the operator's own tests (the catalogue test, the family tests and twins, the clinical sheet, the negotiation corpus), which measure the system against keys written in this repository, not a benchmark;
  - the worked cases, which are demonstrations (D-S48);
  - the results from before the loop (`docs/fix/*_RESULTS.md`, 25 files): component training and evaluation (the producer's checkpoint 168 and its frozen DEV figure of 102 of 102 items and 75 of 84 rows; the Auditor896 classifier and its tuning runs; the first domain-agnostic tuning pilot), and the ordinary final runs v3 to v12 on the operator's synthetic test. None is a result on a report benchmark, so none is compared. The DEV figure is cited as the component's own measurement under its protocol (`tuning/producer_v3/evaluation_protocol.json`); R1 measured it again under the constraint (section 7).
- **Ablations of contract validity (R1, R2a to R2c):** they measure whether a reply has the form its contract requires, never a benchmark's primary metric (D-S99: ContraDoc binary judgment accuracy, SciTab macro-F1 in its declared class setting) (corrected D-388), so their prompts may come from out-of-scope runs (the synthetic suite, the negotiation corpus) and from the producer's pre-loop DEV set. Each row prints its prompts file's digest and its count of prompts per source, and none of their figures is read as a result on a benchmark.
- **Cost and reliability figures (gap 15):** spend, minutes, pass rates of integrity re-runs and timings (as in `TIME_BUDGET.md`) measure the system, not a benchmark's primary metric (D-S99) (corrected D-388). Each is printed with its run, source file, machine and date, and whether the asset copy matched, and none is compared as accuracy.

## 5. Published systems (D-S73 items 2 and 3; gap 8)

Every result in a results table carries a context column with its published counterpart:

- the system, the model and its size;
- the metric and label set;
- the split and its size;
- the source and its date;
- each difference from our setting, stated beside it (split, label set, document length, prompt form);
- whether the published level was reached, and by how much, on the figures as they stand.

Where any setting differs, the comparison is never called like-for-like. Where no comparable published figure exists, the column says so, and the bar is the untrained form and B1. The published figures come from the target table (D-S73 item 1) once a checker has read it; none is copied from memory.

## 6. A result that fails

It is not compared and appears in no results table. Its lesson may appear as a method finding (D-S74 item 4), citing its decision and stating the condition it failed. Nothing is dropped silently.
